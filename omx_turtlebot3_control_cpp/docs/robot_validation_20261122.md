## Stay 설정 확인

호스트 `turtlebot3_manipulation_bringup/launch/base.launch.py:274`의 `stay_pose_msg`와
로봇의 소스·설치본을 확인했다. 관절 순서는 joint1, joint2, joint3, joint4다.

| 관절 | 저장된 Stay (rad) | 현재 설정으로 환산한 엔코더 (rad) |
|---|---:|---:|
| joint1 | 0.104311 | -0.199418 |
| joint2 | 0.027612 | -2.089282 |
| joint3 | -0.001534 | -0.021476 |
| joint4 | -1.638291 | 0.544563 |

저장된 값은 v6 학습 설정의 Stay와 동일하다. 로봇 설치본은 `--time 4 --rate 0.5`로
발행한다. 실제 ROS CLI 파서에서 `--time`은 `--times`로 해석되므로 **0.5 Hz로 4회 발행**한다.
4초 동안 발행한다는 뜻은 아니다. 각 trajectory의 `time_from_start`는 3초다.

현재 encoder tick은 `[1918, 686, 2034, 2403]`, manipulator 연결 플래그는 1,
팔 토크는 0, ROS 연결 플래그는 0, 전압은 12.11 V였다. 표의 각도는 현재 설정의
영점 2048과 부호 +1로 환산한 값이다. 영점·방향 검증 완료를 뜻하지 않으며, 특히 joint2는
이 환산 기준에서 URDF 하한 밖이다. 이를 통과시키기 위해 영점·관절 제한을 변경하지 않았다.

기존 초기 Stay 이동은 arm_controller가 시작된 뒤 실행하는 ROS trajectory 명령이다.
처음 검증한 C++ 직접 OpenCR 런치에는 이 자동 이동 단계가 없었다. 이후 사용자 요청으로
`mp_control/launch/aruco_pick_place.launch.py`를 확인하고 단일 C++ 포트 소유자 안에
Stay 초기화를 추가했다. 기존 bringup은 토크·바퀴 설정도 수행하고 같은 포트를 독점하므로
새 런타임과 동시에 실행하는 방식으로 연결하지 않는다.

추가한 경로는 deadman → 경로 검사 → 측정 위치/저속 프로파일 사전 설정 → 필요한 경우 팔 토크
ON → C++ 동시 최소 저크 이동 → 위치·속도 안정 확인 → READY 순서다. 읽기 전용에서는
토크가 꺼진 상태의 센서 읽기만 허용한다. 실물 보정 조건과 관절 제한은 그대로 검사한다.
로컬에서 C++ 22개, Python 141개 시험이 통과했다. 가상 직렬 포트에서 토크 OFF 시작부터
Stay 도달과 임무 전환까지 검증했으며, 실제 팔에서 이 동작을 수행한 결과는 아니다.

추가 읽기 전용 시험에서 OpenCR 테이블의 millis 값이 약 20 ms 간격으로 갱신됨을 확인했다.
연속 조회가 같은 카운터를 받는 것을 즉시 고장으로 처리하던 코드를 수정했다. 같은 값을
신선한 입력으로 재사용하지 않고, 동일한 100 ms 읽기 제한 안에서 다음 카운터를 기다린다.
실제 카운터 정지·역행·시간 초과는 계속 거부한다. 초기 프로파일 설정 시간은 Stay 궤적 시간에서
제외한다. 측정 원본은 이번 검증 폴더의 `counter_cadence.json`에 기록했다.

수정 후 Jetson에서도 C++ 22개·Python 141개가 통과했다(기존 선택 시험 1개 제외).

종료 후 `/dev/ttyACM0`와 `/dev/video0`의 소유 프로세스가 없음을 확인했다.

## ONNX 출력 문제 수정

이 Jetson의 OpenCV 4.5.4에서 원본 ONNX를 최종 `action`까지 실행하면 마지막 Clip이
ReLU6로 처리되어 일부 음수를 0으로 만드는 현상을 확인했다. 0 벡터 입력의 원본 projection은
약 `[-0.05597221, 0.17845374, -0.10571495, 0.08587889]`지만 기존 최종 출력은
첫째·셋째 값이 0이었다. fusion·최적화 토글만으로는 해소되지 않았다.

원본 `actor.onnx`를 그대로 읽고 `l3`까지 계산한 뒤 마지막 `[-1, 1]` Clip을 C++에서
수행하도록 수정했다. x86의 Gemm과 Jetson의 InnerProduct import 이름을 확인하며 알려진
v6 모델 SHA-256을 고정해 이 경로를 다른 그래프에 적용하지 않는다. 초기화 시 973개
검증 벡터를 통과해야 하므로 모델 로딩·유한값 검사만으로 제어 준비를 승인하지 않는다.

| 검사 | 결과 |
|---|---|
| Jetson Release 빌드 | 통과 |
| 수정 후 원본 973개 검증 벡터 | 최대 절대 오차 3.57969e-7, 허용 1e-5 이내 |
| Jetson CPU 추론 2,000회 | 평균 15.0546 µs |
| Jetson C++ 시험 | 14개 통과 |
| Jetson Python·C ABI·가상 직렬 시험 | 130개 통과, 선택 Torch 시험 1개 제외 |
| 호스트 회귀 시험 | C++ 14개, Python 130개 통과 |

원본 ONNX SHA-256은 `fe3656701f104022872ad804ac120496c4b31de8cf9e7c3a2f94250e4ceef00c`로
변하지 않았다. 학습 체크포인트, residual 비율과 물리 보정 플래그도 변경하지 않았다.

## 실제 통합 런치 및 카메라

단일 런치는 모델 검사 후 카메라와 C++ 런타임을 모두 시작했다. 런타임은 토크가 꺼진 상태를
감지해 종료 코드 1로 중단했고 카메라도 함께 종료됐다. 이 실행을 통합 제어 성공으로 기록하지 않는다.

첫 카메라 실행에는 메모리 매핑 오류도 있었다. V4L2 mmap 3·4 버퍼 독립 캡처는 각각 3프레임
통과했고, 별도 ROS 재시험에서는 7초 동안 RGB 영상 200장과 CameraInfo 199건을 수신했다.
해상도 320×240, rgb8, 이미지 프레임은 `eef_usb_camera_optical_frame`이었다.
CameraInfo의 frame_id는 비어 있어 기존 정확한 타임스탬프 쌍 바인딩이 계속 필요하다.

마지막 실제 영상에서 ID 0·1 검출은 성립하지 않았다. 파란 물체 앞면 마커의 하단이
영상 경계 밖으로 잘려 있었다. 관측 품질 조건이나 모서리 검사를 완화하지 않았다.
이 결과는 카메라 스트림 수신 확인이며 세계 좌표·마커 외부 보정 완료는 아니다.

종료 후 이번 시험의 제어·카메라 프로세스와 장치 점유는 남아 있지 않았다.
