# C++ 매니퓰레이터 제어 구현 및 검증

| 항목 | 기준 |
|---|---|
| 구현일 | 2026-08-02 |
| 패키지 | `omx_rl_control_cpp` |
| 언어 | C++17, ROS 2 Humble, Eigen3 |
| 대상 모델 | `arm_delivery_pitch_hold_v4` |
| 실기기 구동 | 수행하지 않음 |

## 1. 구현 목표와 선택

기존 Python 런타임의 ROS 인터페이스와 PICK/PLACE 제어 경로를 C++에서
재현한다. 단순 joint nudge 노드가 아니라 다음 항목을 함께 옮겼다.

- 학습과 동일한 33차원 관측
- Stable-Baselines3 PPO의 deterministic actor 순전파
- 목표 bearing에 따른 joint1 회전
- 두 개의 접근 waypoint와 numerical pregrasp IK
- reference + PPO 10% residual
- EMA, 위치·속도·가속도 제한
- `joint2 + joint3 + joint4 = 0` 그리퍼 pitch 결합
- ArUco/pose/base/관절 freshness gate
- 비동기 GripperCommand, HOLD, FAULT, E-Stop
- `/rl_control/status`, `/mp_control/status`, `/target/base_hold` 호환 출력

v4의 `supported_commands: [PICK, PLACE]`와 네 phase를 그대로 사용한다.
파지 후 `WAIT_DELIVERY`에서는 그리퍼를 닫은 Stay를 유지하고 외부 베이스
운반을 허용한다. 배송지 정지 후 `PLACE_REACH → OPEN_RELEASE →
PLACE_TO_STAY → COMPLETE`를 수행한다.

## 2. SB3 모델의 C++ 변환

`policy.zip`은 Python pickle/PyTorch 자료를 포함하므로 로봇의 C++ 런타임이
직접 해석하지 않는다. 학습 PC에서 `export_sb3_actor.py`가 다음 actor만
고정 바이너리로 내보낸다.

```text
observation[33]
  -> Linear(33, 256) -> Tanh
  -> Linear(256, 256) -> Tanh
  -> Linear(256, 4)
  -> clip[-1, 1]
```

| 파일 | SHA-256 |
|---|---|
| 원본 `policy.zip` | `ce5403ddffaf69181801400959824700346d28b64bb559bab93fcdbe16f9aafb` |
| C++ `policy_actor.bin` | `379a38e4866ba2d6f57942f61998ec74f685c50984fc3a0f6e005764987e70d4` |

바이너리 헤더에는 magic `OMXACTR1`, format version, 33/256/256/4 차원을
기록한다. C++ 로더는 magic, 버전, 차원, 모든 weight의 유한값, 정확한 파일
끝을 검사한다. 출처와 checksum은 `policy_actor.yaml`에 남긴다.

## 3. 패키지 구조

```text
omx_rl_control_cpp/
├── include/omx_rl_control_cpp/
│   ├── policy_actor.hpp
│   └── runtime_math.hpp
├── src/
│   ├── policy_actor.cpp
│   ├── runtime_math.cpp
│   ├── rl_control_cpp_node.cpp
│   └── policy_probe.cpp
├── models/arm_delivery_pitch_hold_v4/
│   ├── policy_actor.bin
│   └── policy_actor.yaml
├── launch/rl_control_cpp.launch.py
├── tools/
│   ├── export_sb3_actor.py
│   └── compare_cpp_policy.py
└── test/test_runtime_math.cpp
```

`runtime_math`는 ROS에 의존하지 않아 FK, 관측, reference와 action limiter를
단위 시험할 수 있다. `policy_probe`는 ROS/PyTorch 없이 actor 입력 33개를
받아 행동 4개를 출력하므로 Python SB3와 직접 비교할 수 있다.

## 4. Python과 C++의 관계

| 항목 | Python | C++ |
|---|---|---|
| ROS client library | `rclpy` | `rclcpp` |
| PPO 추론 | SB3 + PyTorch, CUDA/CPU | Eigen CPU |
| 모델 입력/출력 | 33 → 4 | 33 → 4 |
| actor 계산 | PyTorch float32 | Eigen float32 |
| reference·안전 계산 | NumPy float64 | Eigen double |
| 기본 노드명 | `rl_control_node` | `rl_control_node` |
| 토픽·Action | 기존 계약 | 동일 계약 |
| PICK/PLACE 네 phase | 지원 | 지원 |
| release 안정화 후 Stay | 지원 | 지원 |

C++ 구현은 CUDA나 Python 가상환경 없이 동작한다. 다만 actor 크기가 작아
CPU 추론이 충분하다는 전제이며, 실기기 timing 측정 전에는 성능 우위를
단정하지 않는다.

## 5. 실행 선택

기본 통합 실행은 기존 Python을 유지한다.

```bash
ros2 launch turtlebot3_control omx_turtle.launch.py \
  control_runtime:=python
```

C++ 런타임은 명시적으로 선택한다.

```bash
ros2 launch turtlebot3_control omx_turtle.launch.py \
  control_runtime:=cpp
```

두 구현은 같은 노드명과 출력 토픽을 사용하므로 동시에 실행하지 않는다.
독립 fake-hardware 확인은 다음 진입점을 사용한다.

```bash
ros2 launch omx_rl_control_cpp rl_control_cpp.launch.py \
  start_hardware:=true use_fake_hardware:=true
```

controller timing, gripper 접촉과 실기기 성공률까지 보장하지 않는다.

## 7. 실기기 적용 전 확인 순서

1. C++ 패키지를 로봇에서 빌드하고 `policy_actor.yaml` checksum을 확인한다.
2. `start_hardware:=false` 상태에서 노드 시작과 actor 로딩을 확인한다.
3. fake hardware에서 `/joint_states`, status, trajectory와 E-Stop을 확인한다.
4. 실제 하드웨어는 물체 없이 Stay 상태에서 `initialize_to_policy_stay=false`로
   시작해 현재 자세 확인만 수행한다.
5. 저속·넓은 안전 공간에서 수동 PICK 한 번을 확인한다.
6. 물체 없이 fallback 또는 측정된 delivery pose로 PLACE 경로를 확인한다.
7. ArUco 자동 PICK, 외부 운반, PLACE와 timeout HOLD를 확인한 뒤 반복
   배송 시험으로 넘어간다.

현재 작업에서는 실제 로봇을 움직이지 않았다.
